# View as (developer impersonation)

The owner asked (2026-11-05) for a temporary mode where the developer uses the web app as any other account, without its password, to test what that account sees and does.

## Rules

1. Starting needs the permission `user.impersonate.all`, granted to the developer role only, by migration. Code checks the permission by name, never the role slug.
2. The target must be another account (not yourself), active, and must not hold `user.impersonate` in any scope. That is how "a developer cannot view as another developer" is checked without the role name.
3. The developer never sends or sees the target's password. Start takes only the target id and an optional reason.
4. While viewing, these abilities are refused whatever the target's role holds, and are left out of `/auth/me` permissions: `user.manage`, `role.manage`, `user.impersonate`. So nothing done while viewing can create accounts, change passwords, change role grants or start a second view-as.
5. A view-as lasts 30 minutes from its start (`ViewAs::MINUTES`), then the next request gets 401 and the browser goes to the login page. It also ends on "return to my account" and on logout.
6. The app behaves exactly as the target account: `Auth::user()`, permissions, nav, landing page, scoping, and the `created_by`/`updated_by` columns on business rows are the target. The request log keeps the target too.
7. The audit log names the real person. While viewing, every `audit_log` row has `user_id` = the developer and the new column `on_behalf_of` = the target. The audit page shows the target under the actor.

## Sessions

A view-as is a `user_sessions` row for the target with two new nullable columns: `impersonator_id` (the developer's user id) and `expires_at`. Only one token is ever in the browser.

- **Start** (`POST /api/v1/auth/view-as`, `permission:user.impersonate`): in one transaction, deletes the developer's presenting session, creates the target session, writes `VIEW_AS_STARTED`. Answers 201 with the login response shape for the target.
- **Return** (`POST /api/v1/auth/view-as/end`, `auth` only): the presenting session must be a view-as session, else 409. In one transaction, deletes it, creates a fresh session for the developer, writes `VIEW_AS_ENDED` (`ended_by: returned`). Answers 201 with the login response shape for the developer. If the developer is no longer active or is locked, the view-as still ends and the answer is 401.
- **Logout** while viewing deletes the view-as session and writes `VIEW_AS_ENDED` (`ended_by: logout`) instead of `LOGOUT`. The developer is then signed out.
- **The guard**, on a view-as session, ends it (soft delete + `VIEW_AS_ENDED`) and answers 401 when it has expired (`ended_by: expired`) or when the developer or the target is no longer active, is locked, or the developer no longer holds `user.impersonate` (`ended_by: revoked`). A view-as the browser abandons leaves only its start row; that row carries `expires_at`.
- **Revocation from the console** ends a view-as at once with `ended_by: revoked`: deactivating or setting the password of the target or of the developer (`User::revokeSessions`, which then deletes the account's other sessions as before), and terminating the view-as session from the target's session list (which still writes `ADMIN_SESSION_TERMINATED` too). Return on a revoked view-as answers 401, so no developer session is minted.

## Audit rows

| event | user_id | entity | old_values | new_values |
|---|---|---|---|---|
| `VIEW_AS_STARTED` | developer | `users` / target | `{session_id}` (the developer session it replaced) | `{session_id, expires_at, reason}` |
| `VIEW_AS_ENDED` | developer | `users` / target | `{session_id}` (the view-as session) | `{ended_by, session_id}` (`session_id` only for `returned`: the developer's new session) |

Every end of a view-as writes exactly one `VIEW_AS_ENDED`: `returned`, `logout`, `expired` (guard) or `revoked` (guard or console). Nothing ends one silently.

## API shapes

Login, start and return all answer:

```json
{ "token": "…", "token_type": "Bearer", "idle_timeout_seconds": 28800, "user": Profile }
```

`Profile` (`/auth/me`) gains `view_as`: `null`, or `{ "by": { "id": "…", "name": "…" }, "expires_at": "ISO-8601" }`.

Start body: `{ "user_id": uuid, "reason": string|null (max 500) }`. Refusals are 422 validation errors on `user_id` with the keys `identity.view_as.self`, `identity.view_as.not_allowed` (target holds `user.impersonate`) and `identity.view_as.inactive`.

`GET /audit-log` rows gain `on_behalf_of`: `null` or `{ id, name }`.

## Web app

- `Me.view_as` drives a banner above the header on every page: "You are viewing as {name} ({role}) until {time}" with a "Return to my account" button. Return swaps the token, clears the query cache and goes to `/`.
- `/console/accounts` shows a "View as" row action when the signed-in account can `user.impersonate`, on active accounts other than itself. It opens a dialog with an optional reason; confirming swaps the token and goes to `/`, so the target's landing page applies. A refusal shows the API message.
- The audit page shows "on behalf of {name}" under the actor when `on_behalf_of` is set.
